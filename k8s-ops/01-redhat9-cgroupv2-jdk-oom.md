# RHEL9 전환에 따른 cgroup v2 미인식으로 인한 JVM 애플리케이션 OOM

## 1. 배경

### 가. 추진 배경

1) RHEL 8.10 EOS(지원 종료) 도래와 RHEL 9.x 지원 여부에 대한 고객사 문의에 대응하기 위해 RHEL 9.x 지원 검증을 진행
2) 현재는 RHEL 8.10과 9.x를 병행 지원 중

### 나. 증상

1) RHEL 8.10 → 9.4 업그레이드 테스트 과정에서 JVM 기반 애플리케이션 파드들 중 일부가 OOM으로 강제
   종료되는 이슈 발생
2) dmesg 로그에서 커널이 해당 파드의 java 프로세스를 cgroup memory 초과로 강제 종료한 것을 확인

### 다. 원인

1) RHEL 9.x는 기본 cgroup 버전이 v1에서 v2로 전환됨
2) OpenJDK 8u362 이하 버전은 cgroup v2를 지원하지 않아(지원은 8u372부터 추가) 컨테이너의 memory
   limit을 인식하지 못하고, 호스트 전체 메모리를 기준으로 MaxHeapSize를 계산
3) 실제 확인한 사례로, 동일 파드의 MaxHeapSize가 cgroup v1 환경 0.5GiB → cgroup v2 환경 약 30GiB로
   증가 — 컨테이너 limit을 초과해 커널 cgroup OOM killer에 의해 강제 종료됨

## 2. 원인 좁혀가기

| 순서 | 가설 | 검증·조치 | 결과 |
|---|---|---|---|
| 1 | 애플리케이션 메모리 누수 (구버전 JVM은 기동 후 확보한 메모리를 반납하지 않고 계속 사용) | memory limit 상향(3 → 5GiB) 후 사용량 관찰 | 늘린 limit까지 계속 차오름(3.84GiB 사용) — 누수·부족보다 "JVM이 limit을 모르고 힙을 크게 잡는" 쪽을 의심 |
| 2 | OS 업그레이드에 따른 런타임 환경 변화 | RHEL9 릴리스 노트 확인 | 기본 cgroup 버전이 v1 → v2로 전환된 점 포착, OpenJDK 8u362 이하는 cgroup v2 미지원 확인 |
| 3 | 원인이 OS 버전이 아니라 cgroup 버전인가 | RHEL8에서 GRUB 파라미터만 cgroup v2로 변경해 재현, JDK 버전이 다른 파드와 대조 | 동일 증상 재현, 다른 JDK 버전 파드는 영향 없음 → JDK의 cgroup v2 미인식으로 **확정** |

## 3. 기대효과

### 가. 근본 원인 해소를 통한 안정적 업그레이드

1) 리소스 부족이 아닌 JVM 런타임의 cgroup v2 미인식이 근본 원인임을 규명해, limit 상향 같은
   임시조치가 아닌 JDK 버전 업그레이드로 근본 해결

### 나. 표준화를 통한 재발 방지 확대

1) OpenJDK 8u362 이하를 사용 중인 파드를 전체 목록화해, 이후 RHEL9 전환 작업의 사전 점검
   체크리스트로 표준화

### 다. AS-IS / TO-BE 비교

| 항목 | AS-IS | TO-BE |
|---|---|---|
| OS 기본 cgroup 버전 | RHEL8, cgroup v1 | RHEL9, cgroup v2 |
| JVM memory limit 인식 | 정상 인식 (0.5GiB) | 미인식 → 호스트 전체 기준(약 30GiB)으로 오판, OOM 발생 |
| 조치 전 JDK | 8u362 이하 | 8u372 이상으로 업그레이드 |
| 사전 점검 범위 | 개별 이슈 대응 | 구버전 JDK 사용 파드 전체를 사전 점검 표준 항목으로 반영 |

## 4. 조치 흐름

```
STEP 1  RHEL 8.10 → 9.4 업그레이드 중 JVM 파드 OOM 발생 확인
  │
  ▼
STEP 2  memory limit 상향 재현 테스트 — 단순 리소스 부족이 아님을 확인
  │
  ▼
STEP 3  기존 OS에서 cgroup 버전만 v2로 전환하는 재현 테스트로 원인 교차 검증
  │
  ▼
STEP 4  OpenJDK 8u362 이하가 cgroup v2 미지원임을 원인으로 특정
  │
  ▼
STEP 5  영향 파드 전체를 JDK 8u372 이상으로 업그레이드 → 사전 점검 체크리스트로 표준화
```

## 5. 성과

1) OS 업그레이드로 인한 OOM의 근본 원인을 정확히 특정해 근본 해결
2) 구버전 JDK 사용 파드를 전체 목록화, RHEL9 전환 사전 체크리스트로 표준화

### 역할

1) 팀원과 공동 진행 — 원인 분석(RHEL9 릴리스 노트 분석, GRUB 파라미터 기반 cgroup v2 재현 검증)은 본인 수행, JDK 교체·적용은 팀원과 함께 진행

## 6. 회고

1) **가설을 증거로 갈아타기** — 구버전 JVM의 메모리 미반납 특성 때문에 누수를 먼저 의심했지만, limit을 늘려도 계속 차오르는 패턴과 OS 업그레이드 시점이 겹친 점에서 릴리스 노트를 확인해 cgroup 기본 버전 전환을 포착
2) **변수 분리로 원인 확정** — OS를 그대로 둔 채 GRUB 파라미터로 cgroup 버전만 바꿔 재현하고, JDK 버전이 다른 파드는 영향이 없음을 대조해 "OS 버전"과 "cgroup 버전"을 분리 검증
3) **운영 전 발견과 전환 기준 표준화** — OS 업그레이드 테스트 단계에서 발견해 운영 영향 없이 대응하고, 구버전 JDK 사용 파드를 목록화해 RHEL9 전환 사전 점검 항목으로 정착. 호환 JDK는 고객사 업데이트로 배포되는 컨테이너 이미지에 반영
