# Loki 로그 추출/백업 자동화 파이프라인 구축

## 1. 배경

### 가. 기존 문제

1) 기존에는 Java 애플리케이션들이 log4j로 debug 레벨 로그를 NFS에 직접 적재하는 구조였음
2) 다수 애플리케이션 프로세스가 동시에 동일 NFS 볼륨에 로그를 쓰면서 파일 잠금(lock) 경합과
   좀비 프로세스가 발생하는 문제가 있어, 로깅 방식을 중앙집중형(Loki)으로 전환

### 나. 신규 요구사항

1) 로깅 전환 이후, 특정 고객사가 로그 장기보관을 요청 — Loki는 스토리지 비용·보존 기간
   특성상 장기보관에 적합한 저장소가 아니었음
2) 기존 NFS 직접 쓰기 방식으로 되돌아가지 않으면서 장기보관 요구를 충족해야 했고, 워크플로우
   설계부터 CronJob 빌드·테스트·배포까지 단독으로 진행

## 2. 기대효과

### 가. 재발 없는 장기보관 체계 확보

1) 파일 잠금·좀비 프로세스를 유발했던 직접 쓰기 방식으로 되돌아가지 않고, Loki→NFS 백업이라는
   별도 경로로 장기보관 요구사항을 충족

### 나. 통제 가능한 부하로 대용량 추출

1) 시간 분할과 이중 병렬화 설계로, 하루치 로그를 한 번에 긁지 않고도 매일 자동으로 안전하게
   추출

### 다. 2단계 무결성 검증

1) 로컬 압축 무결성 체크와 전송 후 체크섬 비교를 모두 통과해야 원본을 삭제하도록 설계해,
   검증되지 않은 상태로 데이터가 유실되는 상황을 원천 차단

### 라. AS-IS / TO-BE 비교

| 항목 | AS-IS | TO-BE |
|---|---|---|
| 로그 적재 방식 | 앱이 NFS에 직접 write (파일 잠금/좀비 프로세스 발생) | Loki 중앙집중 수집 + 별도 백업 파이프라인 |
| 장기보관 | 불가 (Loki는 장기보관에 부적합) | CronJob이 매일 자동으로 NFS에 아카이빙 |
| 대용량 추출 부하 | 미고려 | 시간 분할(AM/PM) + 이중 병렬화로 부하 통제 |
| 데이터 정렬 | 해당 없음 | logcli 내장 정렬(`--forward`/`--merge-parts`) + 순차 병합 |
| 무결성 보장 | 해당 없음 | 로컬 gzip 검증 + 전송 후 md5sum 비교 2단계 검증 |

## 3. 구성도 (백업 파이프라인)

```
STEP 1  CronJob 기동 (매일, 전일 로그 대상)
  │
  ▼
STEP 2  모듈별 시간 분할 추출 (AM/PM) — 모듈 병렬 2개 + logcli 내부 병렬(2h, 2 workers)
  │
  ▼
STEP 3  AM → PM 순서로 병합 (logcli 내장 정렬 + 순차 병합으로 시간순 보장)
  │
  ▼
STEP 4  전체 모듈 로그를 하루 단위 tar.gz로 압축 → gzip 무결성 1차 검증
  │
  ▼
STEP 5  NFS 장기보관 볼륨으로 전송 → md5sum 비교 2차 검증 → 성공 시 로컬 원본 삭제
  │
  ▼
STEP 6  보존기간(90일) 초과 아카이브 자동 정리
```

## 4. 성과

1) 기존 NFS 직접 쓰기 방식에서 발생하던 파일 잠금·좀비 프로세스 문제를 재발시키지 않으면서,
   고객사가 요청한 로그 장기보관 요구사항을 충족
2) 약 39개 서비스 모듈의 로그를 매일 자동으로 백업하고, 로컬·전송 2단계 무결성 검증까지
   포함한 신뢰 가능한 백업 체계를 구축
3) 시간 분할과 이중 병렬화 설계로, 대용량 로그 추출 시에도 Loki·네트워크에 가해지는 순간
   부하를 통제 가능한 수준으로 유지
