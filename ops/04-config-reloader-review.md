# ConfigMap/Secret 변경 자동 반영 검토 및 부분 구현

TA Unit

## 1. 배경

### 가. 문제

1) 솔루션의 서비스 설정(Nginx 타임아웃/로케이션 블록, Auth의 비인증·프리패스 URL·쿠키 설정
   등)이 추가·변경될 때마다 관리자가 ConfigMap/Secret 변경 후 관련 워크로드를 수동으로
   재시작해야 했음
2) 서비스 모듈 배포가 되지 않는 경우 설정 변경 자체가 반영되지 않는 경우도 있어, 설정 반영
   누락을 방지할 자동화 검토가 필요했음

### 나. 검토 목표

1) ConfigMap/Secret 변경을 자동으로 감지해 관련 워크로드에 반영하는 구조를 검토하고,
   네임스페이스/서비스 모듈 단위로 특정 대상만 선택적으로 재시작할 수 있는 확장 가능한
   구조를 목표로 설정

## 2. 기대효과

### 가. 검토를 통한 무중단 반영 한계 확인

1) Reloader의 기본 rolling restart 대신 SIGHUP 기반 무중단 반영을 검토했으나, 이 방식이
   애플리케이션의 시그널 처리 구현 여부에 좌우된다는 한계를 실증적으로 확인

### 나. 리스크를 고려한 절충 구현

1) 자동화 범위를 전체 자동 재기동이 아니라 "변경 감지"까지로 제한하고, 재기동은 설정
   오반영 위험을 고려해 관리자 확인 후 수동으로 진행하도록 유지

### 다. AS-IS / TO-BE 비교

| 항목 | AS-IS | TO-BE (실제 적용) |
|---|---|---|
| 설정 변경 감지 | 수동 확인 | Reloader 기반 자동 감지 |
| 무중단 반영(SIGHUP) | 검토 대상 | Nginx/go-auth만 가능하다는 한계 확인, 이번 범위에서는 미구현 |
| 워크로드 재기동 | 수동 | 자동 재기동 대신 수동 확인 절차 유지 (오반영 리스크 고려) |
| 적용 범위 | 전체 수동 | 특정 네임스페이스 우선 적용 후 점진적 확대 가능한 구조로 검토 |

## 3. 성과

1) ConfigMap/Secret 변경 시 수동으로 변경 여부를 추적해야 했던 문제를 자동 감지 체계로
   개선해, 설정 변경 누락 가능성을 낮춤
2) SIGHUP 기반 무중단 반영은 애플리케이션의 시그널 처리 구현 여부에 좌우된다는 한계를
   실제 검토를 통해 확인
3) 자동화 범위를 "감지"까지로 제한하고 "재기동"은 수동 확인 절차로 남겨, 설정 오반영 위험과
   운영 편의성 사이에서 안전한 절충안으로 부분 구현
