# Redis RDB Replica 기반 Diskless 원격 백업 구현

## 1. 배경

### 가. 기존 문제

1) 기존 통합 백업 파이프라인(DDL/TRIGGER/DML 덤프를 하나의 아카이브로 묶는 구조)에 **Redis RDB 자체가 백업 대상으로 포함돼 있지 않았음**
2) 수동으로 RDB를 저장한 뒤 파일을 복제하는 방식을 우선 검토했으나, Master에서 직접 저장·복제를 수행하는 구조라 Master 부하 증가가 우려되어 채택 보류

## 2. 기대효과

### 가. Master 부하 없는 백업 구조

1) Master가 아닌 **Replica에서 직접 diskless RDB를 원격으로 받아오는 방식**으로 설계해, 백업 작업이 Master 성능에 영향을 주지 않도록 함

### 나. 배포 구조에 무관하게 동작

1) Sentinel 구성 여부(Sentinel HA / Standalone)를 자동 판별해 백업 대상을 결정하는 단일 로직으로, 서로 다른 운영 환경에도 동일한 스크립트로 대응

### 다. AS-IS / TO-BE 비교

| 항목 | AS-IS | TO-BE |
|---|---|---|
| RDB 백업 여부 | 백업 대상에 미포함 | 정기 백업 파이프라인에 편입 |
| 백업 주체 | (검토안) Master에서 직접 저장 | Replica에서 diskless 원격 백업 |
| Master 부하 | (검토안) 저장·복제로 부하 우려 | 부하 없음 (Replica가 담당) |
| 배포 구조 대응 | 해당 없음 | Sentinel/Standalone 자동 판별 |
| 검증 | 해당 없음 | 1노드·3노드 백업/복원 테스트 완료 |

## 3. 구성도 (백업 흐름)

```
STEP 1  배포 구조 판별 — Sentinel 여부 확인
  │
  ├─ Sentinel 배포(3노드) → sentinel slaves 조회로 Replica IP 추출
  │
  └─ Standalone(1노드) → 기존 노드 IP 사용
  │
  ▼
STEP 2  대상 노드에서 diskless RDB 원격 백업 (redis-cli --rdb)
  │
  ▼
STEP 3  기존 DDL/TRIGGER/DML 덤프와 함께 하루 단위 tar.gz로 압축
  │
  ▼
STEP 4  백업/복원 테스트 — 1노드·3노드 양쪽 구조 모두 정상 확인
```

## 4. 성과

1) Redis RDB를 정기 백업 대상에 새로 편입하면서도 Master 부하 증가 없이 백업이 가능한 구조를 확보
2) Sentinel 유무에 따른 배포 구조 차이를 하나의 백업 로직으로 흡수해, 운영 환경이 달라도 동일한 스크립트로 대응 가능
3) 1노드·3노드 두 구조 모두에서 백업 무결성 및 복원 테스트를 정상 완료
