# OpenEBS NDM 메모리 누수로 인한 노드 OOM 대응

## 1. 배경

### 가. 증상

1) 고객사로부터 노드 메모리 과사용으로 OOM이 발생한다는 신고 접수
2) Grafana 리소스 대시보드로 확인한 결과, `openebs-ndm` Pod의 메모리 사용량이 특정 시점부터 지속적으로 우상향해 정상 범위를 크게 벗어나는 것을 확인

## 2. 기대효과

### 가. 정확한 근본 원인 특정

1) 단순 리소스 부족이 아니라, 상용 백업 솔루션이 생성하는 가상 디바이스의 메타데이터를 NDM(Node Device Manager)이 가져오지 못해 스캔이 행(hang)에 걸리며 메모리가 누적되는 구조적 원인을 로그 분석으로 특정

### 나. 무중단 조치

1) ConfigMap 설정 변경과 DaemonSet 롤링 재기동만으로 조치가 끝나, 서비스 다운타임 없이 문제 해소

### 다. AS-IS / TO-BE 비교

| 항목 | AS-IS | TO-BE |
|---|---|---|
| NDM 스캔 대상 | 접근 불가 가상 디바이스 경로도 계속 스캔 | 문제 경로를 `path-filter` exclude로 제외 |
| 메모리 사용량 | 지속 증가 후 OOM 발생 | 정상 범위(수백MB) 유지 |
| 조치 방식 | - | ConfigMap 수정 + 롤링 재기동, 다운타임 없음 |
| 재발 방지 | - | 동일 백업 솔루션 설치된 타 노드 사전 점검 |

## 3. 구성도 (조치 흐름)

```
STEP 1  Grafana 리소스 대시보드로 openebs-ndm Pod 메모리 급증 확인
  │
  ▼
STEP 2  NDM 로그 분석 — 접근 불가 디바이스 경로 반복 스캔 확인
  │
  ▼
STEP 3  근본 원인 특정 — 백업 솔루션 가상 디바이스 메타데이터 조회 실패로 스캔 행(hang)
  │
  ▼
STEP 4  node-disk-manager.config의 path-filter exclude에 문제 경로 추가
  │
  ▼
STEP 5  DaemonSet 롤링 재기동 (다운타임 없음) → 메모리 정상화 확인
  │
  ▼
STEP 6  동일 환경의 다른 노드 사전 점검으로 재발 방지
```

## 4. 성과

1) 로그 분석과 공식 문서 근거를 바탕으로 NDM 메모리 누수의 근본 원인을 정확히 특정
2) 설정 변경만으로 조치를 완료해 서비스 영향 없이 문제를 해소
3) 유사 환경의 다른 노드까지 사전 점검 범위로 넓혀 재발 가능성을 선제적으로 확인
