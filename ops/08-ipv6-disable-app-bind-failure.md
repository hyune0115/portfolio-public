# 커널 IPv6 비활성화로 인한 애플리케이션 기동 오류 대응

## 1. 배경

### 가. 증상

1) IPv6 소켓(`::80`)에 바인딩하는 애플리케이션에서 기동 오류가 발생

## 2. 기대효과

### 가. 정확한 원인 특정

1) 애플리케이션 자체 결함이 아니라, 고객사가 커널 레벨에서 설정한 IPv6 비활성화와 애플리케이션의 IPv6 소켓 바인딩 설정이 충돌하는 구조적 원인임을 규명

### 나. 네트워크 스택 단순화로 재발 원천 차단

1) 불필요한 IPv4/IPv6 듀얼스택 설정을 제거하고 IPv4 단일스택으로 통일해, 커널·애플리케이션 설정 불일치로 인한 재발 가능성과 불필요한 리소스 사용을 함께 방지

### 다. AS-IS / TO-BE 비교

| 항목 | AS-IS | TO-BE |
|---|---|---|
| 네트워크 스택 | IPv4/IPv6 듀얼스택 (커널은 IPv6 비활성화 상태로 불일치) | IPv4 단일스택으로 통일 |
| 애플리케이션 바인딩 | 일부 애플리케이션이 IPv6 소켓에 바인딩 시도 → 기동 실패 | IPv4 소켓으로만 바인딩하도록 설정 수정 |
| 클러스터 마스터 컴포넌트 | `0.0.0.0` 광범위 바인딩 | 불필요한 광범위 바인딩 제거 |

## 3. 구성도 (조치 흐름)

```
STEP 1  IPv6 소켓 바인딩 애플리케이션 기동 오류 발생
  │
  ▼
STEP 2  커널 설정 확인 — ipv6.disable=1 확인
  │
  ▼
STEP 3  IPv6 사용 애플리케이션 전수 확인
  │
  ▼
STEP 4  애플리케이션 설정에서 IPv6 바인딩 제거 (IPv4 전환)
  │
  ▼
STEP 5  클러스터 마스터 컴포넌트 바인드 주소 정리
  │
  ▼
STEP 6  IPv4 단일스택으로 통일해 재발 방지
```

## 4. 성과

1) 커널 설정과 애플리케이션 설정 간 불일치라는 근본 원인을 정확히 특정
2) 애플리케이션·클러스터 마스터 컴포넌트 양쪽 모두 IPv4 단일스택으로 정리해 재발 가능성을 원천 차단
3) 사용하지 않는 프로토콜 스택 제거로 불필요한 리소스 사용도 함께 방지
